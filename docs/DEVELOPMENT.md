# OP Ultra 开发者技术说明

本文对应当前老 P7 研究实现 0.6.4，说明如何取得数据、合成画面及送到仪表，以及继续拓展时需要保留的边界。它不是其他车辆可直接套用的刷机教程。

## 1 设备与运行方式

中控是 Android 9／骁龙 820A，仪表是独立运行原厂程序和 Kanzi 显示的设备。两者通过车内网络及厂商接口通信。

OP APK 运行在中控，负责 CarPlay、数据读取、卡片和地图合成。宽幅接收程序运行在仪表侧，在会话期间使用临时目录和前景 framebuffer。当前方案没有替换仪表固件或 Kanzi 布局，也没有停止原厂 ECluster 主程序。

必须区分三件事：

1. 能连接 CarPlay，不代表能读取车辆权限接口。
2. 能通过原厂小地图接口提交图像，不代表获得整屏图层的访问条件。
3. 中控取得 root，不自动意味着另一台仪表也允许部署、执行和访问显示设备。

本项目在匹配的自有车辆上已经走通宽幅输出。移植时应重新确认仪表管理通道、架构、显示设备、恢复状态和执行权限，不能只删除 E28／API28 检查。

## 3 两条地图路径

### 3.1 独立地图来自哪里

中控主画面与独立仪表地图分别作为 CarPlay 视频流接收和解码，现有实现区分主屏 type 110 和独立屏 type 111。独立流不是中控截图，因此主屏切换应用不会天然截断仪表地图。

手机端是否给出独立画面、采用何种视野、是否包含车道级导航，仍由 iPhone、iOS 和地图应用决定。向手机声明更大画布是显示能力协商，不等于能请求任意一套地图 UI。

### 3.2 原厂小地图模式

```text
iPhone 独立视频
 → ClusterMapRenderer／取景
 → 按原厂请求尺寸编码 JPEG
 → 本机受限 socket
 → P7InstrumentWorker
 → 原车导航图像接口
 → 原厂仪表地图区域
```

本车协商采用过 1328×664 的独立画布，实际原厂地图请求为 660×660。取景后的图像按真实请求尺寸提交，而不是把猜测尺寸写死成通用值。

该路径复用原厂地图卡片通道。需要处理原厂地图生产者的临时交接、重复提交保活和退出后的恢复，不能让两个图像生产者持续争用同一通道。

### 3.3 Ultra 宽幅模式

```text
iPhone 独立视频／独立解码纹理
 → 按 Ultra 画布取景与有界读回
 → ARGB8888 地图缓冲
 → Android Canvas 合成车况、导航、封面和卡片
 → 最后一次 RGB565 转换
 → 无损分块载荷
 → 中控传输／仪表接收端
 → 仪表前景层与原厂背景融合
```

Ultra 当前画布为 1920×720。仪表端接收的是中控已经合成的像素，不是在仪表端硬解 H.264／HEVC，也不是仪表端运行浏览器或 Android View。

原厂 Kanzi 继续绘制自己的背景。OP 不重新实现原厂 SR、完整告警队列或全部充电动画；图层显示得像整屏，不代表接管了仪表的全部逻辑。

## 4 高德识别与取景

`SecondaryMapNavigationState` 根据当前会话的导航来源和状态，判断是否为高德且正在导航。只有该条件成立时，`P7InstrumentFraming` 使用对应校准；结束导航、切换来源或换机后回到默认取景。

原厂小地图与 Ultra 的画布不同，校准必须分开：

| 路径 | 当前条件与处理 |
| --- | --- |
| 原厂小地图 | 在 1328×664 中取 664×664；默认横向起点 332，高德导航中为 544 |
| Ultra | 仅 1920×720 且高德导航中采用横向采样起点 -115，其余保持原画布 |

这些值是当前研究车与手机输出的校准结果，不是 CarPlay 协议规定。负采样区域由纹理边界延展填充，不会生成额外道路信息。不同手机和地图版本出现定位偏差时，应对照独立流原图、合成图和实际仪表图定位，不应盲目改变所有地图的偏移。

## 5 车辆数据读取

`UltraDataService` 在受限的 root／shell 辅助服务中，通过车辆已有的 `android.car.jar` 和相应厂商 API 读取数据。主 UI 不持有任意命令入口，不发送驾驶执行器控制指令。

主要已接入字段如下。方法名仅代表当前车的接口，不是跨车型稳定 SDK：

| 读数 | 当前 getter 或来源 | 展示处理 |
| --- | --- | --- |
| 车速 | `getVcuRawCarSpeed` | 范围、新鲜度检查后取整为 km/h |
| 挡位 | `getVcuGearState` | 按本车实测枚举映射 D／N／R／P |
| 电量 | `getVcuElectricQuantityPercent` | 有效范围内显示百分比 |
| WLTP 续航 | `getVcuWltpAvailableDrivingDistanceFloat` | 结合续航模式，拒绝无效值 |
| 本次行程 | `getLastStartUpMileage` | 距离，单位 km；它不是时间 getter |
| 充电后里程 | `getLastChargeMileage` | 与本次行程分开显示 |
| 总里程 | `getDriveTotalMileage` | 保留在数据页，较低频率读取 |
| 平均能耗 | `getVcuAvgVehiclePowerConsume` | kWh/100km |
| 电池功率 | `getVcuChargeDischargePower` | 有效范围内保留正负，曲线来自当前运行采样 |
| 胎压 | `getTpmsTirePressureValue` | 本车数值除以 100 后显示 bar；轮位参数需重新核对 |
| 胎温 | `getTpmsAllTireTemperature` | 四轮数组、长度与范围检查 |
| 外温 | `getHvacExternalTemp` | 标为“空调外温”，不冒充另一个显示源 |
| 四门、前盖 | `getBcmDoorsState`、`getBcmBonnetStatus` | 按已确认状态映射；未知值显示缺失 |
| 充电状态 | `getVcuChargeStatus` | 已读取，尚未形成完整充电页面调度 |

后台也尝试采集部分电池电流、电压、其他续航制式、行程 A／B 等字段，但“代码存在读取项”不等于均已实车验证、接入卡片或稳定支持。尾门 getter 在本车未完整可用；汇总依赖所有必要字段，不应用四门正常替代尾门已关闭。

当前调度对车速、挡位使用约 100ms 周期，SOC／续航约 1 秒，胎压、能耗和行程距离约 2 秒，总里程约 5 秒。方法反射缓存，失败按类别记录；UI 使用已经收到的快照，设置页切换不会新建一组硬件轮询。

数据封装保留字段状态、采集时间和 age。主界面还检查快照的 schema、来源、辅助服务身份与连接状态。不要把缺失值写成 0，也不要为了“看起来正常”取消过期检查。

## 6 行程时间为何单独处理

原厂把启动后、充电后、行程 A、行程 B 的距离／时间放在同一轮转信号中：`host_trip_distance_time`，结构可理解为 `[kind, km, minutes]`。

已确认启动后对应 kind 0，时间单位是分钟；OP 将其转换成内部秒字段，显示时再换算为分钟。`getLastStartUpMileage` 只提供用于核对的启动距离。

读取逻辑使用正常 D-Bus 行程信号，而非生产环境内存扫描，并处理：

- 只接受 kind 0 的启动后行程，不把充电后或 A／B 时间混进去。
- 与独立 SDK 读取的启动后距离交叉核对。
- 按仪表启动代次和时间戳去重，拒绝上一轮行程及跨重启的旧缓存。
- 对原厂四类轮转使用 10 秒有界缓存，不因重复数据或空订阅续期。
- 一次有界订阅未遇到 kind 0 属于正常空窗口，不因此进入持续增长的 IO 故障退避。
- RPC 与辅助订阅各自有截止时间，仅结束本项目创建的子任务。

管理通道整体阻塞时，本地超时不能释放远端已经卡住的原厂任务。此时应报告通道不可用，而不是无限重试或宣称重装即可修好。

## 7 iAP2 导航与音乐

### 7.1 导航摘要

`RouteGuidanceState` 按当前控制会话维护增量状态，解析 `0x5201` 的相关参数：

| 参数 | 含义 | 单位／处理 |
| --- | --- | --- |
| `0x04` | 目的地名称 | 字符串；空值和“未知位置”等占位不当作真实目的地 |
| `0x05` | 预计到达 | 时间戳，验证范围后格式化为本地时间 |
| `0x06` | 剩余时间 | 秒 |
| `0x07` | 到目的地的剩余路程 | 米 |
| `0x0A` | 下一转向距离 | 米，与到目的地的剩余路程分开 |
| `0x0D` | 当前机动项索引列表 | 用于关联转向明细 |
| `0x13` | 导航来源 | 用于来源切换与特定取景条件 |

`0x5202` 解析机动项索引、类型、转入道路和驾驶侧。通过索引与当前机动项关联，转换为 `RouteTurnIcon`，由 Canvas 绘制图标。不能沿用上一机动项方向来填补新的未知类型。

所有字段先完成边界、重复项和编码校验，再修改状态；错误消息不能只更新一半。切源、导航结束、会话结束、过期时清理对应数据。首次来源信息晚到时保留同会话刚收到的新鲜导航字段，避免误清空。

“有目的地字段”与“手机确实发了真实名称”必须分开诊断。当前数据页可显示名称或导航状态，主卡片选择稳定可得的转向行。

### 7.2 音乐

`CarPlayNowPlayingView` 提供当前歌名、歌手、封面和进度。封面采用独立有界异步解码，只在内容改变时更新，不在每帧重新解码。

音乐卡片上方是较大的歌名，下方是歌手，长文字单行省略。它不是歌词界面，现有协议处理没有形成可用歌词源。

原车方向盘控制通过媒体按键请求机制接到 CarPlay。已确认 NEXT 行为，不应据此把所有播放器、所有媒体按键或所有蓝牙组合标为通过。

## 8 UI 与原车图层融合

`UltraDashboardView` 在 Android 上绘制固定逻辑坐标的 1920×720 画布，UI 预览按比例显示。左右卡片目前各为 480×512，卡片可以互换位置；原车仪表仍不支持触控。

半透明效果是低分辨率地图背景柔化、底板、细描边与封面色彩光晕的组合，不是浏览器实时滤镜，也不是 Kanzi 中新增了一个 Liquid Glass 材质。

上下由仪表接收端融合，保留原车信息区域；当前实现涉及顶部 96 行、底部 60 行，采用所确认的“40% 地图占比”设计模式及非线性权重。**40% 是设计模式名称，不是全屏逐像素固定 `alpha=0.4`。** 原厂文字／图标通过 color-key、底色识别和相应保护逻辑透出。Android 不再给整张地图叠加第二遍上下色罩。

原厂状态带中的告警、字体颜色和背景可能随主题及页面变化。保留图层、做像素检查与恢复机制不等于已经完成全部告警认证。新主题、未知底色、读失败或页面切换，应保留现有回退逻辑。

原车素材在本地研究版中用于贴近原车风格，未随本公开构建分发。公开版本使用系统字体和 `UltraPublicArtwork` 的原创绘制，详见 `ASSETS.md`。

## 9 仪表接收与恢复

### 9.1 临时前景层

`ultra_app_receiver.c` 在使用前检查本车前景层的分辨率、虚拟尺寸、像素格式、步长、blank、位置和相关显示状态。它记录原状态与像素备份，再配置匹配的宽幅前景层。

原厂背景 framebuffer 只读；接收端写入其持有的前景层，并做上下融合。不能把该实现描述为“完全不改变任何显示配置”，但它不替换系统固件、原厂布局或后台显示程序。

停止、EOF、持续缺帧和退出路径触发恢复。恢复包含原前景几何、像素和显示状态的核对。接收端有独立父级恢复路径；Android 侧还等待 `RESTORE_OK`，未确认则保留故障状态。

暂时缺帧可以让出原车显示并沿现有连接恢复，不把一次 UI 绘制延迟直接判为永久断流。持续丢失则结束本轮并走恢复流程。

### 9.2 模式交接

`UltraOutputRouter` 串行管理宽幅接收端与原厂小地图 worker：

1. 停止当前输出的继续生产。
2. 等待当前输出释放、恢复确认和相应租约日志清理。
3. 确认前景层或原厂小地图路径可用，再启动目标输出。
4. 恢复未确认时不启动第二个写入者。

不能通过同时保留两个投放服务来减少切换等待，这会重新引入抢图、闪回原车地图和恢复竞态。最新三态切换已实现，但完整长时间往返及异常交接组合尚未全部实车覆盖。

## 10 性能与调度

当前目标是减少整条链路的等待和重复工作，而不是缩小安装包。

- **合成一次再转色**：地图与图层先用 ARGB8888 合成，最后一次转 RGB565，避免每层重复读写和抖色。
- **复用资源**：有界地图缓冲、位图租约、封面缓存、背景柔化缓存和字段方法缓存，旧会话的迟到结果不能污染新会话。
- **只准备下一帧**：上一帧等待仪表 ACK 时，最多预备一帧，不产生无限渲染或网络积压。
- **精确 ACK 背压**：序号、返回时间与预算检查通过后才继续；不把 socket 写完当作仪表已展示。
- **分块无损传输**：使用 RGB565 与 LZ4 分块格式，在不额外做 JPEG 有损压缩的情况下减少传输。tile 解码检查载荷与输出范围。
- **减少碎片写入**：固定网络头合并写入，避免小写入增加控制等待。
- **独立线程**：绘制输出、车辆读取、封面解码与主线程分工；保持正常线程优先级，不依赖提高整车 CPU 频率或修改全局调度。
- **按模式关停无用工作**：小地图或关闭模式不继续运行 Ultra 的整幅合成导出。

在本车一次约 50 秒、同有线连接的性能样本中，宽幅投放整体约 9.3fps，预热后的部分窗口约 9.3～9.8fps。该样本不是最新 UI 包的全场景认证，也不是恒定 10fps、长期温升或电池能耗结论。RGB565 减少带宽，同时也有颜色精度低于 ARGB8888 的取舍。

改动后至少分别记录手机输入、解码输出、读回、绘制、转换、编码、传输、ACK 及恢复状态。手机输入慢、解码慢、合成慢和仪表 ACK 慢应分开定位。

## 11 授权和安全边界

当前可用入口包括匹配车辆上的原厂授权服务，以及用户已经运行并授权的 Shizuku。原有 ADB 入口只用于已开启且信任的 ADB。项目没有因此获得所有 P7 都能免初始化、免授权运行的能力。

原厂入口只启动本包受限辅助服务及固定动作。当前代码校验包名、签名、UID 和车型／API 条件，并对 IPC 的动作、长度和模式值做约束。UI 不应增加可由外部 Intent 传入任意命令、路径或网络目标的功能。

本包固定授权区分：

| 用途 | 所做准备 | 不包含 |
| --- | --- | --- |
| 原车热点 | 本包 `WRITE_SETTINGS` AppOp 及结果核对 | 全局放开其他应用、强行切频段 |
| 有线 CarPlay | 本包 VPN、麦克风及当前可见 Apple USB 设备访问 | 代替 iPhone 信任、解除系统 USB 过滤、重载框架 |
| 车况／仪表 | 启动并连接有权限的固定辅助服务 | 获取任意车控权限、自动修改仪表固件 |

有线连接中的 VPN 用于应用内 USB 网络通道，不能因为名字叫 VPN 就当作访问外部代理。远程认证则确实使用用户配置的服务地址，应分别说明和审查。

仪表传输使用本车内部网络和固定协议，其版本标记与哈希检查不等于 TLS、秘密口令或完整对端认证。不要把管理通道或接收端暴露到公网。公开代码、功能测试和签名校验不构成完整独立安全审计。

## 12 构建和二次开发注意事项

当前 Android 工具链以源码 Gradle 配置为准：JDK 25、Android Platform 37、Build Tools 36.0.0、NDK 28.2.13676358。目标车仍是 API28；构建 SDK 版本与车辆系统版本不是同一概念。

在完整 SDK／依赖已准备好的环境中，Android 层可用：

```bash
unset OP_MFI_ASSETS_DIR
./gradlew -Pp7Profile=true -Pp7ViewAreas=true :mobile:assembleDebug
./gradlew -Pp7Profile=true -Pp7ViewAreas=true \
  :common:testDebugUnitTest :shared:testDebugUnitTest :mobile:lintRelease
```

Windows 使用 `gradlew.bat` 和相同参数。当前研究构建启用了上述 P7 显示参数；这些开关不代表所有尺寸变化都已无缝。没有注入个人认证材料的构建需由使用者自行配置认证。

当前 Ultra Android 包名为 `com.heavendoor.opultra.carplay`，与普通 OP 分开。自行签名的包不能直接覆盖维护者签名的包。

**自己编译还需处理两种固定校验，不能只改包名签名：**

1. `OwnRootService`、`UltraDataService` 等检查签名指纹；使用自己的签名时，应一致更新为自己的公钥指纹并保留身份校验。不要把维护者私钥当作构建依赖，也不要直接删除校验。
2. 仪表接收端和辅助资产有固定摘要。修改 native 后应重新编译、校验并更新对应摘要，避免 APK 与实际接收端不一致。

仪表接收程序为匹配仪表的 32 位 ARM 原生程序，中控 Android JNI 与仪表接收端不能互换。接收端实现采用受控入口、静态链接／低依赖方式，并包含基础指令路径及可用时的 NEON 路径。

原生程序构建入口为 `python3 scripts/build-instrument-native.py --ndk /path/to/ndk`，支持 macOS／Linux NDK。脚本从 `native/` 编译两个辅助程序，并更新源码中的对应资产摘要。完整步骤见 `BUILD.md`；Windows 可编译 Android 层，重建仪表 native 可使用 Linux 环境。

## 13 已验证范围与继续拓展

本研究车辆上已经观察到：

- 真实独立 CarPlay 地图进入原厂地图区域及 Ultra 宽幅界面。
- 车速、SOC、WLTP、胎压、胎温、部分行程与能耗读数；其中若干项已与原车逐项核对。
- 真实歌曲封面、名称、进度与导航剩余信息。
- 正常停止投放后恢复原车画面，以及宽幅链路的短期性能提升。

当前公开包 519 项 JVM 检查通过，1 项依赖私用认证材料的检查按条件跳过；Android 绘制／生命周期、12 组日夜卡片及实际帧传输夹具通过，Lint 无错误。这些覆盖代码行为，不代替全车型、全部车况与长期行驶验收。

后续拓展可优先分层进行：

| 方向 | 可复用部分 | 仍需补足 |
| --- | --- | --- |
| 更多车辆信号 | 字段封装、缓存、新鲜度和数据页 | 原厂 getter、单位、枚举及静态／动态交叉验证 |
| 新信息卡片 | Canvas 画布、主题和封面等资源管理 | 卡片布局及可信数据来源；歌词目前无可用实现 |
| 更好地图取景 | 导航来源／状态、独立流及 profile | 各地图和手机版本的独立输出实测 |
| 充电界面 | 已采集充电状态、输出关闭与恢复链路 | 原厂页面优先级、可靠让出与恢复时序 |
| 更高帧率 | 有界预备、ACK、分块与耗时计数 | 路测、温升、持续带宽和接收端实际预算 |
| 新车型仪表 | 协议和渲染分层思路 | 新硬件的执行入口、图层定义、权限、恢复，不是改常量即可 |
| 更完整恢复 | 单一输出者、租约、备份和状态机 | 锁车／上电、通道阻塞、系统强停和掉电组合 |

建议先让数据源和输出路径可独立验证，再增加新 UI。新增 getter 不应夹带车控写入；新增仪表输出不应绕开恢复确认；新增缓存不应把未知状态伪装成有效车况。
