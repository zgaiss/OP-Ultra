# 原车弹窗适配的实现方案

本文对应 v0.6.7。原车仍负责车况、告警判定和上游选中状态；OP 读取这些状态，以自己的界面绘制提示。这里没有复用原厂弹窗像素，也没有修改 Kanzi 资源或刷写仪表。

## 数据与绘制分工

```text
中控原厂车辆 / 音频接口
  → UltraComfortReader：100ms 只读采样
  → UltraComfortState：有效期、初始基线、事件序号与剩余寿命
  → UltraProjectionRunner：64 字节状态消息 + ACK
  → 仪表 op_self_popup：缓存字形、日夜皮肤、单个提示条

仪表原厂 Cluster D-Bus 服务
  → op_alert_source_linux：一条监听、两次初始状态读取
  → op_alert_source：解析、状态校验与通道隔离
  → op_text_alert：纯文字告警、分层状态与局部绘制

已解码地图和卡片画布 + 当前提示状态
  → op_widget_compositor / op_widget_present
  → 完成合成后提交到前景图层
```

中控不为每次弹窗生成一张全屏图片。仪表也不解码 CarPlay 的 H.264/HEVC；它接收原有地图合成帧，并在本地补画提示。

## 温度、风量和媒体音量

`UltraComfortReader.java` 通过原车 `android.car.jar` 的 `xp_vehicle` 以及系统 `IAudioService` 读取：

| 信息 | 读取方法 |
| --- | --- |
| 主驾设定温度 | `getHvacDrvSeatTempValue` |
| 记忆风量挡位 | `getHvacFanSpeedLevel` |
| 空调总开关 | `getHvacPowerState` |
| 媒体音量 / 静音 | `getStreamVolume(3)` / `isStreamMute(3)` |
| 最大风量 / 音量 | 连接时读取并缓存 |

空调总开关与记忆风量分别处理。已知关闭状态归一成风量 0，显示“空调 · 已关闭”，不要求原厂风量 getter 同时变成 0；开启时使用有效挡位。未知开关值、异常返回和不支持的属性不能解释成关闭。缺少开关方法的旧接口保留原挡位读取回退。

初始读数建立基线，不产生操作提示。媒体音量额外等待至少 2000ms，并要求当前值及静音状态稳定至少 300ms，再启用变更提示；失效后恢复或重新激活读取时重新建立基线。这不是用户意图识别：静默基线期间的实际调节也不会弹条，但不拦截调节、不延迟声音。温度与风量不等待媒体基线。

读取错误不延长旧数据新鲜度。750ms 内的单次失败保留原值，超过有效期隐藏；恢复时重新播种，不把恢复值当成用户操作。

### 小消息格式与交互

提示状态沿现有仪表 TCP 会话传输，使用独立消息类型和 ACK，不另开公网接口。消息体固定为 16 个小端 32 位整数，共 64 字节：版本、日夜/静音位、三类读数及最大值、三个事件序号、三个剩余寿命和三个保留字段。

只有状态变化才发送消息。当前发送点位于地图帧传输循环：已经收到的提示可以独立完成动画，但地图读取或传输长时间阻塞时，新读数的送达也可能受到影响。

- 提示条位于 1920×720 坐标中的 `(650, 566)`，大小 `620×76`；连同阴影的脏区为 `(634, 554, 652, 106)`。
- 最后操作优先；同类就地更新，不重建外壳；跨类型切换只更换内容，没有等待队列。
- 最后一次变化后显示 2500ms，120ms 进入、80ms 退出、跨类内容过渡 65ms。
- 日夜配色来自当前仪表主题。温度 ≥27℃ 使用暖色；这是显示配色阈值，不是对实际出风冷热的判定。

## 纯文字告警

仪表使用现有会话总线、对象 `/com/xiaopeng/DomainController/Cluster`、服务 `com.xiaopeng.DomainController.Cluster`：

```text
get_host_ealarm_id
get_host_mcu_eautopilot_tips_id
org.freedesktop.DBus.Properties.PropertiesChanged
```

先建立一条订阅，再通过两个正常 getter 获取初始状态。返回值按原厂 `((iiix), i)` / 属性 `(iiix)` 格式解析，检查返回状态和时间戳；255 / -1 清除语义与真实 ID 0 分开。进程路径、身份代次及总线所有者变化会使旧状态失效。

普通告警与辅助驾驶提示分开维护，不能把 ID 大小当优先级。同 ID 更新不反复入场，重叠层结束后恢复仍有效的下层。状态机保留独立高层提示的表达，但绘制能力不代表已经验证其所有真实来源。

`native/alert-data/` 提供 197 条静态文案和通道成员数据；这不等于 197 类告警都已实车接通。当前两路读取获得的是原厂选中状态，不能仅凭 getter 就保证最终像素显隐、完整仲裁和退场动画与原厂完全一致。

未知 ID、未确认的专用布局、缺初始状态或监听故障时，让原车显示层接管；不猜测 ACC 无法激活的原因，不靠安全带状态拼出原厂未发出的告警。原车地图、关键告警和恢复结果仍需对应固件的实车验收。

## 绘制与开销控制

`op_self_popup.c`、`op_text_alert.c` 在仪表本地绘制；动画不等待地图的下一帧。活动动画按约 16ms 的期限调度，这是调度间隔，不是保证实机 60fps。

- 字形、文字断行和皮肤离线生成；运行时不逐帧加载字体或排版。
- 文字告警使用固定尺寸档位、三项背景缓存及三项成字面板缓存。
- 单条舒适度提示与分层文字告警由同一合成器仲裁，避免两者相互擦除。
- 在普通 RAM 草稿中完成地图、卡片和提示合成后再提交；动画只提交合并后的脏区，不先在可见缓冲上擦掉提示再补画。
- 没有动画时等待下一次事件或期限；原厂订阅的检查和异常读取都有边界，不按 197 条文案创建 197 个监听或轮询。
- 增加的开关读取仍在同一 100ms 采样任务中，没有新增高频线程或音频缓冲。

这些方法减少重复工作，不代替仪表端的 CPU、温升、帧率和长时间使用测试。

## 拓展与构建

新增提示应先确认真实接口、单位、初始状态、失效及清除语义，再接入选中状态。不要只新增一条文案就宣称一种告警已支持，也不要用固定倒计时替代原厂长驻告警。

公开版提示字形由 Noto Sans CJK SC 生成，许可证和版权通知在 `third_party/noto-cjk/` 与 APK 的 `assets/licenses/`。主界面沿用 Android 系统字体。更改字形或文案时，先运行两份生成器，再重建 native 和 APK；见 [构建指南](BUILD.md)。

本版完成了基线/失效/开关语义的 JVM 检查，以及本地原生显隐、快速切换、绘制边界和清除检查。发布时用户已离车，本次两个显示行为尚未新增实车验收；原车完整告警与全部优先级也未完成验收。
